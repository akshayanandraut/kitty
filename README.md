# Kitty

Kitty is a women-only group planning and money-recording product. The public design preview is deployed at `https://kitty.grasany.com`. The interactive account and group flows are still a **local development slice** using synthetic people. There is no public registration, real KYC, payment collection, or real money transfer.

Run `npm test`, then `npm run dev` and open `http://127.0.0.1:4173`. Local demo identities are accepted only when `KITTY_LOCAL_DEMO=1` and the server binds to loopback. Data persists in `data/kitty.json`; remove that file to reset sample data. This mode must never be enabled in a public deployment.

Production member requests fail closed until Kitty's dedicated Grasany PKCE client, central identity verification projection, approved one-time payment contract, and full authenticated journey are connected and tested. Kitty has its own Supabase project and certificate-verified database connection on Vercel. Profile editing, group creation, application, electorate review, voting, and logged rejection override have server-side source routes guarded by a real product session; these routes are not yet a live user journey. Identity verification does not establish gender or safety. Women-only eligibility is self-attested and subject to moderation.

`npm run build` prepares the public Vercel preview in `dist/`. The hosted `/api/status` function checks dedicated database connectivity and declares identity verification, group operations and checkout closed. The PKCE sign-in endpoints are deployed but return `identity_unconfigured` until Grasany issues Kitty its own client ID. `/api/public` serves only opt-in public circle and meetup summaries. The public page does not accept real member data. Git auto-deploy is disabled so publication uses a reviewed, explicit deployment to Kitty's single Vercel project. Motion is decorative and respects `prefers-reduced-motion`; the cat's eyes respond only to local pointer position when motion is allowed.

## Current local flows

- Public discovery shows only opt-in public group summaries and available slots.
- Hosts can open a future meetup to newcomers. Public previews show city, time, theme, typical monthly cost and capacity, while venue and reservation details stay among members. An optional random suggestion requires a click and can be declined before any join request.
- Members can create groups, request or accept invitations, vote on applications, join a waitlist, and belong to multiple groups. An applicant explicitly shares a profile snapshot with verified members of that group. At least half the frozen eligible electorate must vote yes; rejection starts a group-specific three-month cooldown, with a logged verified-admin override.
- Group members can schedule events and RSVP, record member-defined contribution obligations and payments, propose shared expenses with exact integer-paise splits for members or event attendees, and record settlements. Each included person confirms an expense share before it is agreed. These are records only.
- Hosts can rotate and set rules. Members can report or block users. Contact details are shared only by explicit consent within an authorized group. Member removal and report resolution are not yet implemented.
- A hosting cycle records the assigned event host, completed hosting and explicit exceptions. Cancelled meetings never count as hosted. The next cycle starts only after all current participants have hosted or have an exception. Exception approval is currently a single group-host action; a multi-member approval rule is pending.
- Members can export their own record snapshot or request local account deletion.

The local API keeps a serialized transaction queue and writes snapshots atomically. It is a development adapter, not a production database. The Git migrations in `supabase/migrations/` were applied to Kitty's dedicated Supabase project on 2026-10-20, and the private voting tables and photo bucket were verified over certificate-validated TLS. The Vercel database credential is configured as a Production secret. Production code still needs authenticated Grasany SSO, face-photo upload and authorized serving, an actual WhatsApp verification provider, central identity status projection, group moderation and removal policy, approved payment contract, protected heartbeat key, and real user journey verification. The private photo bucket has no browser access policy and no active upload path.
